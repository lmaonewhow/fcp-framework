# FCP UI contract v1

This package is framework-neutral TypeScript for trusted, declarative plugins. It does not load remote JavaScript, evaluate expressions, render raw HTML, expose authentication tokens, or accept data-source URLs. `index.ts` exports the versioned catalog types, strict validator, runtime and two transport adapter factories. Native integration and browser acceptance are separate from the executable Node contract tests.

## Fixed compatibility

The plus-ui factory targets `5.6.2-v2.6.2` (upstream `d0d451967676707021b9857df529c395b27e90a7`). The soybean factory targets `1.1.3` (upstream `4e625111ce173e5c2f40dbfc47475f2849c58feb`). Both adapters are version `1.0.0`, accept contract `1.0`, page schema `1`, and declare their component and host slot lists. Catalog revision is a separate monotonically increasing safe integer scoped to an identity epoch. No compatibility with other upstream versions or React implementation is claimed.

## Required host integration points

Create an adapter with trusted `HostBindings`, then `new UiRuntime(adapter)`. Host bindings must map `context.get/subscribe` to identity, tenant, language and permission changes, and must notify on login expiry, logout and permission revocation even if user and tenant IDs do not change. Never supply tokens through `Identity` or page data. Request bindings use a fixed authenticated capability endpoint; the plugin only receives a capability identifier. Server authorization and enabled-state checks remain mandatory on each call. Plus-ui results use `{code:200,data}`; soybean results use `{data,error:null}`. Host error codes preserve authentication, permission, disabled plugin, stale version, missing dependency and validation errors.

`replaceCatalog` is the transaction boundary: first stage all page routes, menus and slot mounts and check collisions with existing host routes, then atomically swap the FCP-owned snapshot. Throwing must leave the prior snapshot intact. Do not remove unrelated host routes. Slots are explicitly supplied by the host with component categories and input/output schema metadata; slots support the same declared capability button actions and permission filtering as pages, without arbitrary slot event/input payloads. Host rendering uses only the safe node union (`text`, `field`, `button`, `table`, `stack`) and literal text, never `v-html`/HTML injection. Buttons dispatch through `runtime.invoke(pageId, capabilityId, input)`; a browser cannot authorize itself using catalog permissions.

At startup and hard refresh, call `runtime.refresh(signal => fetchCurrentAuthorizedCatalog(signal))`, then periodically poll or refresh from authenticated revision events. A late revision or response from an earlier identity cannot reintroduce pages. `currentPath` and `restoreDeepLink` connect startup routes to the validated catalog. Null means no currently authorized plugin deep link; preserve ordinary host paths and show a disabled/not-found state for a removed plugin route. On identity change the runtime removes prior routes and slots and clears cache. The host must fetch a new identity-scoped catalog afterward. No background polling is implicitly started.

Mount resource cleanup through `trackSubscription(pageOrSlotId, dispose)`, including renderer subscriptions and component resources. `markDirty(pageId)` enables a nonblocking unsaved-edit notification when a page is removed or changed. Dirty notifications cannot veto disable. The host may offer approved copy/export UI but must never retain an enabled submit path after removal. `dispose()` cancels requests, removes mounts, clears caches and unsubscribes identity changes. `render` is the host rendering extension point; the runtime exposes a deeply frozen snapshot that the trusted host maps to its component library. Adapter bindings must not throw during cache clearing or identity reset cleanup.

## Schema

Every field is explicit; unknown properties fail validation. Page IDs are `<pluginId>:<pageId>` and paths are `/fcp/plugins/<pluginId>/<pageId>`. Required component dependencies use exact `type@1` identifiers. Missing components, unknown slots, invalid namespaces, conflicting paths and incompatible versions reject the complete candidate revision before any mutation. The old revision remains active; the caller should show the structured error. The server must authorize every page and slot contribution in its catalog. An authenticated user's page permissions are also filtered locally for navigation, which is not authorization.

A sample catalog is provided in `example-catalog.json`. It uses no school-specific data or host imports. Trusted host wrappers adapt native component properties and field validation/events to this narrow declarative vocabulary. Extending the vocabulary requires a versioned schema and host deployment, rather than passing arbitrary native props through configuration.

## Executable verification

Run `TSC=/path/to/typescript/bin/tsc tests/frontend-runtime/verify.sh`. This performs strict TypeScript compilation, executes the same Node contract scenarios independently for both response adapters, and prints source commit/hashes. Node 22.18+ can additionally run `node --experimental-strip-types --test tests/frontend-runtime/runtime.test.mjs` directly, but that does not type-check. Neither command proves native Vue builds, real authentication, multi-browser convergence, or server-side disable rejection. Those acceptance scenarios remain NOT_RUN until the parent native integration suite actually executes them.

## Implemented pinned Vue hosts

The actual Vue layer is `integration/frontend-shared/PluginWorkspace.vue` and `usePlugins.ts`, copied to each native `src/fcp` by `tools/native.py`. The plus-ui overlay binds `useUserStore`, the original authenticated Axios instance, `ElButton` and `ElInput`. The soybean overlay binds `useAuthStore`, its original flat request wrapper, `NButton` and `NInput`. Both watch their native identity state synchronously. Their first load and five-second catalog poll call `GET /fcp/ui/catalog`; successful data is `{catalog,context}`. Calls use `POST /fcp/capabilities/{id}/invoke` with `{input,expectedRevision}`. No submitted user/tenant field is trusted or added.

Each pinned router receives one hidden, authenticated, precompiled namespace container for `/fcp/plugins/<pluginId>/<pageId>`. Catalog registration means atomically replacing that container's authorized navigation, content and reserved `dashboard.status` mounts, not registering arbitrary Vue modules. The generic container remains after removal and renders an unavailable state, with no disabled plugin content or submit button. The host's ordinary `/fcp/plugins` menu is gated by the independent `fcp:plugin:view` permission. Existing school/ingestion permissions do not implicitly grant plugin UI access. Native authentication guards and layouts remain in place. A narrow server SPA fallback recognizes valid dotted plugin identifiers; other dotted asset/API paths keep their previous behavior.

The runtime is copied to `src/fcp/runtime/index.ts`. Native integration also touches the generated soybean locale keys, `UiRoutePolicy`, the bounded SPA fallback, and the existing trusted-shell redirect whitelist. It does not replace login, authentication storage, tenant handling, database authorization, or business routes. Field edits use each native input component's proper value/update properties; capability responses render as literal text cells. Vue unmounts removed component trees, while the runtime aborts calls and clears old identity data. Catalog polling is the selected update channel; its configured five seconds is not a measured cross-browser convergence result.

Manifest and browser validators share `tests/runtime-packages/ui-boundaries.json`: IDs at most 128 characters; exact known `@1` components; at most 32 component requirements; at most 128 children; at most 1000 nodes per content tree; node depth at most 13 (root depth zero, consistent with the server JSON structural bound); nonblank literal text/title at most 2048 UTF-16 units; bounded slot order ±1000000. Package list bounds and aggregate catalog list bounds differ intentionally because a catalog combines multiple plugins.

For real Vue lifecycle tests without a browser, after native dependencies are installed run `node tests/frontend-runtime/verify-vue-host.mjs <assembled frontend path>`. This uses that frontend's actual Vue/Vue Router with a custom renderer and explicit test transport, covering initial deep-link catalog restoration, field state, in-flight cancellation, stale response rejection, changed identity, dirty disable and unmount. It is a component-level test, not native login or real-server evidence.

Each user-triggered capability action now creates an idempotency UUID in the trusted Vue binding. Failed/unknown responses keep the original input and key for explicit retry; no automatic replay occurs. The UI blocks input changes or a second action until the user retries or explicitly abandons pending retry information. Abandoning does not cancel a possibly committed server operation. Navigation away is blocked while a result is pending, but logout is never blocked; hard refresh uses a before-unload warning. Identity changes clear pending data and warn the user to verify the unknown operation under the original identity. Retry data is only in memory and is not persisted across browser reloads. Server-side write validation and durable idempotency enforcement remain authoritative.

`UiRuntime.render(ownerId)` resolves only currently registered validated content, then delegates to the adapter renderer. The Vue workspace supplies the actual known-component renderer through this method. Identity comparisons normalize field order and permission ordering before deciding to clear the old epoch. `evidence/context-key-order-before-fix.log` is an isolated regression reproduction with the old comparison restored only in a temporary copy, followed by fixed-source tests; it does not represent a failed production deployment.

## Administrator management surface

`PluginManager.vue` and `usePluginManager.ts` add a management tab inside the existing workspace. Visibility requires both the server catalog's normalized control permissions and the corresponding full permissions in the native authenticated store. Enable/disable management needs `fcp:plugin:manage`; installation and platform grant administration additionally require the platform tenant `000000` and `fcp:plugin:install`. These checks are display guards only; all endpoints independently authorize the request on the server.

Installation reads a selected ZIP of at most 64 MiB, computes and displays SHA-256, and requires explicit acknowledgment of trusted-publisher execution risks. It uploads only after confirmation using `application/octet-stream`, `X-Fcp-Digest`, `X-Fcp-Revision`, and an idempotency key. It never installs a publisher trust key, automatically grants permissions, or automatically enables the package. An uncertain upload retains identical bytes, digest, revision and key for explicit retry in the same identity epoch.

Management reads `GET /fcp/plugins`, generates enable/disable plans, shows the exact dependency closure and plan digest, and requires every affected plugin to be acknowledged before confirming. It shows actual server operation phase/outcome, with read-only status polling. Drain wait/cancel decisions are explicit; cancellation warns that committed transactions do not roll back. The decision endpoint does not have idempotent receipts: unknown decisions cannot be blindly retried. The operator must query actual state before making a new decision.

Platform authorization obtains manifest-declared options from `GET /fcp/plugins/{id}/grant-options`, takes an explicit target tenant, original capability ID, allow/revoke choice and exact data scope, and requests `/grants/plans`. The server alone derives the operation and native permission. The UI displays the complete server-generated changes and requires target/scope acknowledgment plus the exact affected-plugin list before `/fcp/plans/{id}/confirm`. Existing normalized storage grants are displayed as returned, never guessed back into undeclared capability names. Grant confirmation does not enable the plugin.

The original native request clients remain responsible for authentication. These FCP requests set their existing `repeatSubmit:false` option so the native 500 ms de-duplication cache does not persist user input/package data or interfere with explicit same-key retries. This does not turn off authentication, server idempotency, authorization, or any global request policy. Only safe fixed endpoint paths are constructed in trusted shell code. Server identity/context changes clear management lists, plans, package bytes and pending operations; old responses are rejected.

Platform uninstall is a separate, explicit action. The UI freezes the selected package digest/revision, requires acknowledgment that all tenants must already be disabled/drained and business data is retained, and submits only `{expectedRevision,confirmedDigest}`. It never automatically disables dependants or clears business data. The uninstall endpoint has no same-key receipt contract; an unknown result is resolved by querying actual installation state, not blindly replaying the mutation.

The pinned RuoYi super-administrator store can return only `*:*:*` rather than enumerated native permissions. The UI accepts that native wildcard only when the authoritative server catalog explicitly grants the corresponding normalized `manage` or `install` permission. A wildcard alone never shows management actions; platform tenant restrictions remain in force.
