# Isolated runtime plugin compositions

## Scope and activation

This opt-in mode runs one isolated Engine, registry, dependency graph, invocation journal and actual Python/Node process group per immutable system release. It does not dynamically replace the legacy global plugin pointer. Packages are trusted server-side packages, not an untrusted-code sandbox. Plugin capabilities remain mediated by host contracts; packages cannot directly change the business application, framework source, or database schema.

Native activation requires `fcp.runtime.enabled=true`, `fcp.plugin.release.enabled=true`, the shared release router configuration and a system VersionProvider. UI release mode consumes the **same router bean**, not a second rollout decision. Reconcile and disable legacy runtime tenants and finish all legacy lifecycle/version operations before switching modes. Legacy writes and recovery are blocked in release mode; verified package staging remains available. Existing legacy Exchange execution is deliberately incompatible and startup fails if enabled together: a release-aware task/Exchange adapter must be provided, not a fallback to the legacy runtime.

## Composition and permissions

Stage verified archives, register immutable PLUGIN artifacts and a system release with the VersionProvider, then register the matching plugin composition. Every plugin ID/version/SHA-256 must match the system release exactly. Dependencies must belong to that composition and satisfy their declared version range. Activation validates declared storage compatibility and starts actual processes before opening admissions. It never applies plugin DDL.

`fcp_plugin_version_grant` (migration V008) binds each approval to tenant, package ID, version, full package digest, capability, operation, scope, principal kind and principal ID. Granting an older digest never grants its replacement. USER approvals require current native user permissions and current scope; TASK approvals require an exact task identity and bounded expiry as well as the corresponding USER baseline approval. Revocation is `del=1`; neither stopping nor retiring deletes plugin data. Management requires a current platform release administrator, independently of business invoke permission.

The current native adapter obtains class scopes from the existing school assignment table. This is an adapter-specific policy, not a promise that all host frameworks share its schema. Plugin storage is owned by plugin/tenant/scope, not duplicated by release, so old/new packages must pass the same compatible-schema checks.

## Request identity and tasks

Authenticated UI bootstrap or catalog provides a signed affinity. Browser catalog and invocation use `X-FCP-Release-Affinity`; they cannot select arbitrary release IDs. The same decision controls the real UI bundle and actual backend composition. A successful catalog refresh renews a still-valid token for the same release; it does not re-bucket or revive expired/revoked tokens. A pending frontend write retains its original affinity and idempotency key. Identity changes discard the pending UI state rather than transferring it to another user.

Server-created TASKs are pinned durably before execution to their original release, exact package digest and canonical input fingerprint. Replays cannot change payload or move versions. Completed receipts are returned only after live authorization checks. An uncertain side effect remains pending and requires reconciliation; no blind replay or deletion is provided.

`beginDrain` closes new user admission/catalog and new task pins but permits already pinned tasks and admitted calls to complete under current authorization. `status` reports `admission`, `draining`, `pendingTasks`, `activeCalls`, actual process readiness and activation state. `stop` requires admission closed, zero active calls and zero incomplete tasks. A full disable is stricter and is not the retirement drain operation. Tracked tasks persist EXECUTING before any invocation. The explicit task-cancellation endpoint and management UI accept only a new-format executionTracking=1 task still PINNED, after platform authorization, exact task confirmation and a reason. Cancellation records CANCELLED plus an audit entry without deleting data. Legacy PINNED, EXECUTING and UNKNOWN tasks cannot be cancelled; they require a supported effect-reconciliation adapter before retirement.

Emergency router disable is stronger than graceful drain: new task/user invocations and every mediated host callback recheck the live gate. Controlled host effects hold the same router monitor through the host handler, including its transaction commit; route shutdown is not acknowledged until effects already admitted to that critical section finish. After shutdown, new controlled commits are denied. Effects already sent to external systems are not undone. Native database commit behavior still requires its integration gate; a real Python callback fixture alone is not database acceptance.

## Recovery

Normal restart reconstructs only approved enabled compositions and preserves task affinity, invocation journals and draining state. Persisted PID plus OS start identity prevents confusing PID reuse with a live old process. A still-live matching process or unknown launch window refuses automatic recovery and requires operator reconciliation. Known preparation failures whose opened runtimes were successfully closed become `PREPARE_FAILED`, not permanent unknown state. This does not claim automatic reconciliation of arbitrary orphan processes or failed cleanup.

## Evidence and boundaries

Run `bash tests/plugin-multiversion/run.sh`, `bash tests/plugin-multiversion-policy/run.sh`, and `python3 tests/plugin-release-host/verify.py`. These cover actual isolated Python/Node processes, digest grants, dependency isolation, drain/stop, persisted tasks, callback fencing and host application contracts. Policy unit tests use a JDBC proxy; they are not MySQL evidence. Native Spring/MySQL and both real frontend bundles require the separate native release CI gate. No production acceptance, arbitrary-JAR deployment, multi-node leader fencing or untrusted-process isolation is asserted here.

## Native composite executor wiring

Select `FCP_RELEASE_EXECUTOR_MODE=native` for the in-process composition adapter. HTTP remains the default mode. Supply `FCP_RELEASE_ENVIRONMENT`, `FCP_RELEASE_EXECUTOR_LOCK_FILE`, the shared routing key and immutable UI bundle root. The lock file must have an absolute non-symlink path inside an existing owner-only directory. Startup acquires an exclusive OS lock **before plugin recovery** and retains it through executor/host lifetime; contention fails startup. All processes that might operate on the same native runtime data must share this exact lock path. Different per-node paths do not create a distributed lock or a supported cluster. Do not remove or replace a live owner's lock file.

The native adapter obtains an authenticated operator from the current request for every lifecycle action. It does not retain user tokens or synthesize TASK administrators. Its state journal is `system_release_executor`. This mode supports immutable UI and plugin compositions; host code, services, config and schema replacements require a different deployment adapter.

With `fcp.release.observation.enabled=true`, actual plugin invocations feed the deployment-bound `WindowedObservation`. `release_security_incidents` durably records confirmed incidents. By default a returned plugin value has business outcome UNKNOWN, even if transport succeeds or the response claims success. A host-owned `PluginReleaseApplication.BusinessClassifier` bean may provide domain-specific classification from trusted contracts. Missing generation bindings fail closed; the executor owns binding both reachable releases only after the corresponding route mutation succeeds. Metrics are local to this single JVM, not cluster-wide telemetry.

## Live authorization projection

Catalog responses carry a separate `projectionFingerprint` derived from the exact projected catalog, authenticated UI context and live per-capability approval decisions/revisions. `catalog.revision` remains the Engine generation used by invocation; authorization changes never invent an Engine revision. Polling compares the projection fingerprint. A changed approval or expiry aborts stale frontend requests, clears cached results/pending UI state, warns about dirty content, and reapplies the current authorized pages and slots even at the same Engine generation. Missing fingerprints clear the sensitive view rather than silently retaining it. A stale signed release context or disabled release is an explicit forbidden response: the view is cleared and the user must manually refresh after reconciling uncertain writes; polling does not silently re-bucket or replay them.

Permission/identity projection changes discard business request payloads and stale results, but do not authorize repeating an uncertain write with a new key. The mounted plugin workspace retains a payload-free uncertainty fence per tenant/principal, including when that principal returns after a local identity switch. A revoked release affinity cannot be silently replaced for retry. The user must explicitly acknowledge checking the original operation and abandoning its retry information; this is not cancellation of a backend effect. These fences are component-lifetime protection, not durable browser-reload reconciliation. Backend invocation journals remain authoritative.
