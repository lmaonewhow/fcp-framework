# Exchange component evidence

Run `source /workspace/shared/fcp-toolchain/env.sh && tests/runtime-exchange/run.sh` in the shared cloud workspace. The runner compiles Java 17 sources, creates real package ZIPs, installs and dynamically enables roster and mock-exam, invokes real Python subprocesses and host callbacks, serves a synthetic loopback HTTP API, and restarts the exchange coordinator using a real atomic file journal. Storage callbacks in this test are an explicit in-memory fixture. This result does not substitute for native RuoYi, MySQL, UI, concurrent load, or production acceptance.

The tested fixture contract is explicitly Campus-v1 CSV with `student_code,full_name,class_code`; identity is unique within an authorized class. The user has not finalized actual school fields or an Excel format. Each class is limited to 500 rows and is stored in one JSON snapshot record for atomic compare-and-set batch insertion. Existing identities are conflicts, never updated silently. This is a bounded first-phase fixture, not an unlimited roster model. Mock-exam declares its own package, UI page and `exams` storage structure and uses `exam_code,title,class_code`, without core/student edits.

Manual preview persists source, content, fixed mapping and schema versions, package identity, current authorization revision, owner and expiry. Confirmation must supply its digest. Commit revalidates rows and snapshot revision and uses runtime plus storage idempotency. A failed or uncertain task does not advance its source cursor. A pending task preview whose authorization/configuration/package changed fails closed and requires an explicit new approved configuration/job; it never silently refreshes itself. A finite connector sync becomes complete at the last page. The host-owned scheduler refreshes TASK identity every tick; it does not borrow the administrator. Native hosting must supply JDBC StateJournal and currently authorized task context.

Controlled export projects only configured fields, gives an opaque handle, and rechecks current export authority, tenant, owner, class, configuration and expiry on download. Formula-prefix cell values are escaped. No external destination or arbitrary client URL exists. LoopbackConnector accepts only explicitly configured literal loopback HTTP endpoints with redirects disabled and a 1 MiB bounded response.

Integration requirement: generic public invocation must reject `exchange.*` operations, especially commit, and route exchange requests through ExchangeService. Configure native storage and package/capability/task grants explicitly. The scheduler and callbacks are host-only APIs. Initial regression failure and corrected run are retained in `evidence/`.

## Native HTTP and fixed scheduler wiring

`FcpExchangeConfiguration`, `FcpExchangeController`, and `FcpExchangeAdvice` are separate Spring integration classes. They do not modify the existing plugin controller/configuration. Both `fcp.runtime.enabled=true` and `fcp.exchange.enabled=true` are required; default remains disabled. The bean uses native `JdbcStateJournal("exchange-fixtures")`, actual EngineRuntimePort and native HostCapabilities. Every HTTP call builds USER context only through `NativePluginHost.current()` after explicit native Authorization-header checking. No tenant, principal, field mapping, script or URL can be submitted in JSON. The application’s existing native Sa-Token and business grant checks remain mandatory.

Deployment-owner fixture configuration: `FCP_EXCHANGE_FIXTURE_CLASS` is the explicitly chosen synthetic class; optional `FCP_EXCHANGE_CAMPUS_FIXTURE_API` and `FCP_EXCHANGE_EXAM_FIXTURE_API` are literal loopback HTTP endpoints. No endpoint is created or authorized automatically. The two fixed config IDs are `roster-fixture` and `exam-fixture`. Set `fcp.exchange.schedules.enabled=true` only when explicitly intended, with `FCP_EXCHANGE_FIXTURE_TENANT` and optional `FCP_EXCHANGE_FIXTURE_INTERVAL_SECONDS` (default 60, allowed 5..86400). Tasks use exact server-selected principals `roster-fixture-sync` and `exam-fixture-sync`, never a USER or the infrastructure recovery identity. Each timer tick creates a new TASK context and checks current grants before source reads and commit. Missing/revoked authority fails closed and keeps the cursor. The scheduler does not grant itself any permission or implicitly enable/install plugins.

Endpoints under `/fcp/exchange`: POST `/configs/{config}/preview` accepts raw CSV bytes with `application/octet-stream`; POST `/configs/{config}/preview-api` accepts only an optional cursor; POST `/previews/{preview}/confirm` accepts digest and idempotencyKey; POST `/configs/{config}/exports` accepts fields; GET `/downloads/{handle}` returns no-store CSV with a fixed safe attachment filename after current authorization recheck. All have native `fcp:plugin:view` admission plus the service’s live import/export/task and storage/plugin scope checks. There is deliberately no HTTP endpoint accepting TASK identity or changing fixed schedules. Grant/configuration changes remain explicit host administration, not plugin operations.

The controller and configuration compile against real locked RuoYi classes and resolved Spring/Sa-Token dependencies using `compile-native.sh`. This is compile evidence only, not running native authentication/MySQL/server or browser acceptance. Example command:

```
source /workspace/shared/fcp-toolchain/env.sh
FCP_NATIVE_BACKEND=/workspace/shared/fcp-native-compile/upstream/backend \
FCP_MAVEN_REPOSITORY=/workspace/shared/fcp-toolchain/m2 \
  tests/runtime-exchange/compile-native.sh
```

Production school configuration, vendor API credentials, user-finalized schema and multi-instance scheduling remain outside this explicitly synthetic fixture wiring. The native deployment must first provision declared storage through the separate reviewed migration flow, install the trusted packages and explicitly grant user/task/platform/class rights. No default or administrator bypass is introduced.

## Genuine isolated CI acceptance entry point

Run `python3 tools/ci_native.py --ingestion --exchange` only in the existing disposable GitHub Actions job. `--exchange` is explicit, requires the genuine encrypted native login fixture, creates no production defaults, and adds its own localhost API fixture. The native server uses the same real MySQL database but a separate deployment account for declared DDL; runtime remains DML-only. The acceptance script installs the unchanged roster/mock-exam ZIP declarations, plans and confirms each declared schema over HTTP, confirms manifest capability platform grants over HTTP, previews and confirms CSV/API imports, checks conflict rejection and idempotency, and exercises controlled export/download after revocation. It then verifies fixed TASK first-page execution, revoked TASK denial, independently wrong package-digest denial, disabled-plugin rejection before source reads, and durable cursor continuation. MySQL read-only audit evidence verifies the writer is TASK rather than administrator. It never inserts or updates business rows directly with SQL.

The approval-management boundary is explicit: generic platform capability grants have an HTTP plan/confirm interface; exchange orchestration operations and TASK rights currently use fixed host/deployment configuration and do not have a generic authorization UI. The CI fixture seeds only its own test role/class and the exact additional authorization rows as test setup. It does not infer TASK grants from platform grants. Every `fcp_runtime_task_grant` row must specify tenant_id, task_id, plugin_id, capability_id, operation, data_scope, package_digest, revision, del and expires_at. The package_digest must independently equal the installed immutable package and the matching platform grant digest. Default absence, expiry, deletion or mismatch denies execution. The exact fixture task rights are exchange/task and exchange/import plus storage/read and storage/write at class:class-a, and exchange.preview/invoke and exchange.commit/invoke at tenant:000000. The TASK has no lifecycle, schema deployment, wildcard, administrator or export privilege.

Native result is written to `reports/runtime-exchange-native/acceptance.json` only by the genuine CI run, with source package hashes, build ID, checks, elapsed time and native JVM identity. Local `test_native_exchange_fixture.py` covers fixture package determinism, isolation guards, exact digest-bound seeds, genuine login routing and opt-in gating, but cannot establish a native PASS. ## Approved A33 export retention

Generated export snapshots are retained for 24 hours from creation. There is currently no physical temporary export file: CSV is rendered from the persisted `download:<UUID>` snapshot when an authorized download occurs. `expiresAt` in a newly generated export response reflects creation plus exactly 86,400 seconds. Current permissions, owner, tenant, config and field checks still apply throughout retention. Expired snapshots cannot download even if cleanup has not run yet.

`ExchangeService.cleanupExpiredExports()` is a host-only, no-argument maintenance API. It accepts no time, path, tenant, identity, prefix or plugin-controlled selector. It processes at most 100 expired download UUID entries per pass, removes only their generated `rows` content, and keeps owner/config/field/binding/creation/expiry metadata, a content digest, and a durable `cleanupAudit` in the same journal compare-and-set. Receipt, task cursor, preview and business/audit entries are not deleted. Tombstones make retries idempotent; every maintenance pass reloads persisted state so a successful-but-uncertain previous CAS is reconciled before another attempt. Restart continues automatically. Legacy five-minute snapshots have a known creation time inferred as original expiry minus 300 seconds; the approved 24-hour policy is applied to that creation time, so they are not prematurely removed.

`FcpExportRetentionConfiguration` enables the independent `ExportRetentionMaintenance` bean whenever native runtime and exchange are enabled. It starts a scan immediately and repeats every minute, without an extra opt-in flag, under the user's explicit cleanup approval. Thus removal happens on the first available scan after 24 hours, rather than claiming execution at the exact expiry second. Failures are logged without export contents and retried on the next scan. No HTTP endpoint, plugin cleanup capability, database credential or arbitrary filesystem access is exposed.

The complete exchange journal is bounded. New state writes reject an encoded UTF-8 payload over 6 MiB with `RESOURCE_LIMIT` (HTTP 429) before compare-and-set; the storage journal itself has an 8 MiB ceiling. This is not unlimited storage. Retained import previews/content, receipts, cursors and cleanup audit/tombstones need a separately approved future archival/capacity policy. A33 does not authorize deleting those objects, and this implementation does not do so.

`ExportRetentionTest` uses a controllable host clock and actual atomic file journal to verify 24-hour retention, the legacy extension, exact boundary denial, fresh snapshot preservation, prior audit/business/receipt/cursor preservation, before-CAS and uncertain-after-CAS failures, restart, automatic maintenance and stable capacity rejection without changing persisted state. Native compilation includes the independent cleanup bean.

The genuine CI exchange fixture additionally compiles `NativeExportRetentionProbe` outside production assembly. It only targets the exact disposable CI database and `exchange-fixtures` journal, a valid generated handle owned by authenticated native fixture user 1, and whitelisted synthetic student-code output. It validates the original 24-hour policy, ages that one test snapshot's creation/expiry while keeping their difference exactly 24 hours, and waits for the real native background cleanup. It does not change the production Clock or delete any content itself. Its check verifies cleanup audit durability, fresh export preservation and an unchanged canonical digest of all non-download journal entries. Native HTTP then verifies expired-download rejection and a still-valid fresh download. This scenario is NOT_RUN until the real CI run reports its result; local helper compilation is not database acceptance.
