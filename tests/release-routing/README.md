# Release routing contract

Run `bash tests/release-routing/run.sh` with JDK 17+ and loopback sockets. This is a real two-service HTTP component test, not native RuoYi, MySQL, browser, or production acceptance. The default file journal remains single-instance development storage; supply a dedicated JDBC StateJournal for production policy CAS.

`DurableReleaseRouter` accepts only host-created `TrustedContext`. It must never be populated from an untrusted request body. Host permissions guard policy administration and each business request. Policy identity and the signing key remain fixed: changing percentage/revision does not reshuffle buckets. Exclusions beat allowlists. `enabled=false` denies **all** routing, including stable: it is an emergency stop, not a pause button. Pause expansion means retain the current policy. Abort/revoke means change the pair or increment epoch (and switch candidate admission appropriately); decrementing percentage alone retains outstanding compatible affinities until expiry. Epoch cannot decrease. Stable rollback must be checked for data/API compatibility before putting the policy.

Affinity binds tenant, principal kind/id, current authorization revision, release pair, policy id, epoch, and expiration. It is not an authorization token. The host must authenticate and obtain current authorization revision each time, including task calls. An excluded tenant cannot resume a candidate affinity. Old affinity denial is explicit; write requests are never automatically resubmitted to another version. Long tasks need separately persisted release binding and idempotency, not an expired browser affinity.

`ReleaseHttpTransport` has an immutable deployer-owned endpoint map and exact path allowlists. It sends no caller-supplied URL or authorization header and cannot dynamically discover arbitrary services. Each release may be independently registered at a numeric loopback HTTP or HTTPS origin. DNS/egress policy for deployer-configured HTTPS hosts belongs to deployment infrastructure. A separate 32+ byte key authenticates backend request envelopes and binds method/path/body digest. Receivers must call `verifyIdentity`, enforce current authorization, and implement application idempotency; short-lived signatures do not eliminate replay. TLS/secure key distribution remain deployment obligations. Do not use the affinity key as the backend identity key. Response release identity must match the selected release; there are no transparent application-level write retries or redirect following. Timeout/transport/identity failures on writes count as unknown outcome and require reconciliation.

Observations are process-local cumulative counters, reset on restart, not a durable Prometheus window or automatic rollout controller. They distinguish transport/application errors and optional `X-FCP-Business-Outcome: failure` on a trusted backend response, plus unknown write outcomes. Hosts must instrument business rejection truthfully; HTTP 200 alone cannot establish success for every application. Successful responses require `X-FCP-Release` with the registered release id. Metric snapshots are approximate under concurrency and must not be used alone to authorize automatic expansion.

Current module is reusable infrastructure. It does not itself replace existing plugin global runtime registration, update either Vue entry point, deploy services, migrate data, or bypass the existing native permissions. Those integration and end-to-end tests must be completed separately before claiming product gray-release support.
