# Trusted request observation and durable staged rollout

This module is an implementation of manually triggered, operator-approved observation-driven rollout, not an unattended privileged scheduler. A current authenticated USER explicitly enables a policy and invokes `tick`. Every step calls the existing authorized `ReleaseController.advance`; USER credentials are never persisted and TASK identities are rejected. Hosts wanting timers must separately implement and approve a narrowly scoped internal identity. No timer is started here.

`ObservationProvider` is replaceable host configuration. Its windows are trusted source data, never a browser-uploaded MetricsGate.Sample. `WindowedObservation` records real request admission/completion with deployment-generation binding, exact bounded nearest-rank p95, technical failures, explicit business outcomes, unknown writes and incomplete requests. Missing business outcome is UNKNOWN and prevents expansion. The trusted HTTP contract uses X-FCP-Business-Outcome success/failure; this is valid only for a configured trusted service, not arbitrary third-party responses. Stdio plugins should use `ObservedInvocation` with a host-owned semantic classifier; the default is UNKNOWN, never inferred success from arbitrary plugin JSON.

The collector is single-process and keeps at most 256 route bindings and 32 generation windows, at most 10,000 latency samples per window. Overflow, incomplete windows, source failure, unknown generation and insufficient samples fail closed. Old evicted generations become unavailable, not healthy. A restart creates a new source epoch and requires a new complete dwell window. It does not claim distributed aggregation or persisted performance samples. The optional third constructor parameter is a dedicated StateJournal for durable, append-only security incidents (at most 1,000). Production hosts should supply JDBC for this journal; confirmed generation-bound incidents then survive collector restart even with no performance samples. The two-argument development constructor has only process-local incident memory.

Both stable and candidate release IDs must be bound to the actual router revision and deployment generation. LocalProcessDeploymentProvider optionally receives WindowedObservation and does this before the expected CAS route publication. No unbound request is silently credited as healthy. A failed publish has no matching traffic; conflicting reuse of a release/revision binding is rejected. Actual traffic hooks are in ReleaseHttpTransport. `ObservedInvocation` is the reusable equivalent for other transports.

DurableRolloutAutomation stores the approved increasing stages, limits, dwell, owner, step and immutable pending operation. Windows before approval are discarded. A pending step reuses its original operation identity and release CAS; executor work is never independently retried by this module. Existing pending release work requires the release controller's reconciliation. PAUSED never resumes automatically. FULL finishes this rollout policy; continuing production health monitoring remains a separate host responsibility. Disabling a policy stops new automatic decisions, not existing release execution or traffic. A pending step must first be reconciled; disabling does not silently discard an unknown operation. Use the release controller ABORT endpoint for emergency ingress containment.

Native opt-in integration uses fcp.release.observation.enabled with fcp.release.enabled and requires an actual ObservationProvider bean. No default empty or synthetic provider is installed. `/fcp/releases/automation/state`, `/enable`, `/disable`, `/tick` use existing explicit release permissions and native identity. Enable accepts stages, minimumDwellMillis, minimumSamples, maximumAgeMillis, maximumErrorRate, maximumP95Millis and expectedRevision. Tick has an empty request body; sending observations is rejected. The default native HTTP executor does not magically acquire monitoring by enabling this property.

Run `source /workspace/shared/fcp-toolchain/env.sh && python3 tests/release-observation/verify.py`. Tests use two actual loopback Python child services and persistent file journals, proving HTTP200 business failures close governed ingress, missing business signal pauses, healthy windows expand to full, pre-approval traffic is excluded, explicit security incidents take precedence, and a policy-intent interruption resumes one immutable step. This is not native RuoYi/MySQL/browser/production acceptance. Raw logs and source hashes are recorded under reports/release-observation. No malicious plugin sandbox, global percentile, OS kill of the controller, or production SLO is claimed.

Recovery rechecks trusted security incidents before applying any saved performance decision. A later incident creates a separately persisted `-security` containment operation; it never changes an accepted expansion's identity. An already pending executor requires advertised fenced containment. Otherwise the policy preserves its pending record and reports `CONTAINMENT_REQUIRED_PROVIDER_NOT_FENCED`, without claiming ingress stopped. A missing security source cannot authorize recovery of a healthy expansion. Existing fail-closed pause/abort decisions may still execute. The observation state machine distinguishes an explicitly confirmed pending security tick from ordinary mutations; unknown client outcomes and permission checks still block automatic retries. The parent release console must separately distinguish authoritative core pending from a local unknown write before enabling this entry point; this patch does not relax that parent lock or claim the integrated native UI path is accepted.

`POST /fcp/releases/automation/safety` is a separate containment-only entry point with exactly `expectedRevision`, `expectedReleaseRevision`, and `pendingOperationId`. It requires the current authorized policy owner, an existing automation intent, and the same pending core operation (or its independent containment operation). Under the native single-owner/shared-controller contract, the controller monitor covers snapshot validation through containment submission. Any changed revision, completed pending operation, or unrelated new plan is rejected for fresh confirmation. A healthy check never reads performance windows, reconciles deployment, or advances rollout. Unknown security sources preserve the pending evidence. This endpoint is not a multi-JVM transaction or a substitute for the native executor ownership lock.

Pending safety checks cover both the approved sample generation and server-owned execution generations. An accepted command can already route generation N+1 while its outcome is withheld and the controller still reports observed generation N. Both are checked using the matching persisted command/receipt and immutable approved plan, never browser-provided generation values. Unrelated releases and generations outside this set are not treated as that rollout's incident. A source failure for one relevant generation does not mask a confirmed incident in another; without a confirmed incident, source failures remain blocked.
