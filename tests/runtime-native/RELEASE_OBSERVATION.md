# Native identity-echo observation acceptance

Default behavior remains UNKNOWN. The optional deployment setting `fcp.release.identity-echo.enabled=true` installs a host-owned classifier only for exact plugin/capability/package SHA-256 bindings in `FCP_IDENTITY_ECHO_BINDINGS_FILE`. The file has format 1 and bindings with plugin, capability, sha256, contract=`identity-echo/1`. No HTTP request can register a classifier or report metrics/security incidents.

This narrow contract checks actual invocation input/message, trusted tenant/principal/kind, immutable package version, and the exact result shape. Unknown fields, dependencies and malformed values do not become success. A mismatched trusted identity is rejected by the host and recorded against the actual selected route revision's generation, including late completions. Persistence errors reject the invocation; they never convert it into healthy evidence. This is not a generic business success classifier or malicious-plugin sandbox. Other domains implement the existing BusinessClassifier interface.

The synthetic Python candidate deliberately returns a wrong tenant for one explicitly named negative-test message. Its exact package digest is deployment-approved. Native CI uses real encrypted login, MySQL, Redis, Spring, package verification and subprocess invocation. The independent `native_observation_acceptance.py` module runs after the existing composition scenario: new governed plans, real healthy traffic, automatic EXPAND/PROMOTE, a second plan with a real rejected identity violation, observed STOPPED and late stale command/affinity rejection. It never injects Samples, security booleans, generations or policy state through the browser or SQL. A private strong randomly generated routing key is selected so the synthetic platform tenant naturally falls into the canary cohort; this is test deployment configuration, not a routing bypass.

Component results do not imply native acceptance. Run the existing isolated native CI `python tools/ci_native.py --ingestion --plugin-releases`; native results belong to that exact build and remain NOT_RUN/BLOCKED until executed. Production remains NOT_ACCEPTED.

The opt-in bindings file must be an absolute regular file owned by the service process user, with no group/other permissions and no symlinks in the path. `ProtectedDeploymentConfig` is shared host infrastructure: it requires POSIX owner protection, opens with NOFOLLOW, reads at most 65,537 bytes and rejects anything over 65,536, rejects malformed UTF-8 and detected replacement/size/mtime changes. Deployment should place it in a protected private directory and set its owner to the service user. This helper does not edit permissions automatically. Invalid or unsupported configuration fails startup rather than creating a permissive classifier.

The capability endpoint intentionally retains HTTP 503 for a host-detected result identity violation: the plugin may already have executed, so this is not an authorization denial or proof that a write was undone. This acceptance case recognizes only the exact native typed envelope (`HOST_RESULT_IDENTITY_VIOLATION`, no business result, supported trace identifier). Ordinary 500/503 responses still fail. The diagnostic report records whitelisted protocol status/code, selected release/generation and package digest before asserting, then separately requires genuine observed STOPPED and stale-command rejection. The CI advice probe loads the actual built native JAR and its bundled Spring classes, rather than substituting a mocked advice/controller. It tests the ResponseEntity contract; it does not replace the live HTTP check. The earlier failing run did not preserve its response body, so its exact HTTP response cannot be retroactively claimed.
