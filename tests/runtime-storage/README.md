# Runtime plugin storage evidence

`StorageValidationTest` is a pure Java boundary test, not MySQL or process acceptance. It rejects undeclared fields, wrong types, SQL-shaped identifiers, forged tenant scopes and access before authorization. `MysqlStorageTest` is an executable actual-JDBC test and deliberately exits 2/BLOCKED when an explicitly provisioned dedicated database is unavailable. It never creates accounts, databases, grants, or cleans up data. Apply reviewed native migrations with a deployment identity first; the runtime identity should have only the required DML rights, never DDL.

Compile with the repository Java toolchain:

    javac -d /tmp/fcp-storage-classes core/src/main/java/fcp/{Json,Schema,FcpException}.java core/src/main/java/fcp/plugin/PluginManifest.java core/src/main/java/fcp/host/*.java core/src/main/java/fcp/control/StateJournal.java core/src/main/java/fcp/storage/*.java tests/runtime-storage/*.java
    java -cp /tmp/fcp-storage-classes StorageValidationTest
    java -cp /tmp/fcp-storage-classes fcp.storage.StorageDeclarationTest
    java -cp /tmp/fcp-storage-classes:<mysql-jdbc-jar> MysqlStorageTest

The latter reads FCP_STORAGE_TEST_URL, FCP_STORAGE_TEST_USER, FCP_STORAGE_TEST_PASSWORD, FCP_STORAGE_TEST_DEPLOY_USER, and FCP_STORAGE_TEST_DEPLOY_PASSWORD. Supply them from owner-only private configuration; never commit or print credentials. A test URL is not a substitute for verifying the target is the dedicated acceptance database.

Implemented: bound tenant/plugin/principal/data-scope storage; live authorization including replay and precommit; declared typed fields; bounded keyset pagination and equality-only queries; transactional optimistic revisions, digest-checked scoped idempotency receipts and audit; explicit del=1 and restore with uniqueness conflict detection. No uninstall path deletes records or schema. Each collection locks its schema row during writes, deliberately serializing mutations to enforce declared uniqueness.

The logical migrator adds nullable declared fields only. The deployment-only physical migrator generates owned table names and supports CREATE, ADD_NULLABLE_FIELD and checked nonunique physical indexes. It commits intent before DDL, inspects actual information_schema on retry, and records completion or reconciliation-needed failure. A previously COMPLETE step whose structure disappeared is rejected as drift, not silently recreated. MySQL DDL is not transactional.

`StorageDeploymentService.plan(plugin, manifest.storage)` produces a digest-bound review plan. `apply(context, plan, confirmedDigest)` uses only the separately supplied deployment DataSource, serializes deployment per plugin, verifies additive declared migration operations, checks existing data for newly declared uniqueness, and publishes schema metadata only after all DDL steps finish. Running plugin capabilities cannot invoke deployment. Uniqueness is enforced by the host under the same schema row lock as every physical mutation and scoped to tenant/data scope/del=0, allowing deletion and explicit conflicting restore behavior without destructive SQL. Runtime DML credentials must not be exposed outside this host adapter.

`JdbcPluginStorage` routes registered physical collections to `JdbcPhysicalStorage` through the same five storage capabilities; physical table names never come from plugin input. Physical mutations implement scoped optimistic CAS, digest-bound replay, live grant rechecks, audit, explicit deletion and restoration. Physical PUT updates supplied fields and preserves omitted existing fields, allowing compatible older plugins to avoid destroying newly added fields. Supported physical values are bounded strings (up to 512 characters), exact integers within JSON's safe numeric range, DECIMAL(20,4), booleans, local DATETIME(6) timestamp strings and JSON. Indexes are limited to four declared non-JSON fields and MySQL's 3072-byte budget. Destructive migrations, arbitrary SQL, SQL expressions, table-name input and automatic schema rollback are rejected.

`JdbcStorageCompatibility.verify(plugin, packageVersion, packageDigest, declaration)` is read-only and checks the deployed declaration version/digest, explicit compatible versions, required fields/indexes, every physical column/index and complete contiguous DDL checkpoints. Connect it using `runtime.setStorageCompatibilityVerifier(new JdbcStorageCompatibility(runtimeDml)::verify)`. It cannot deploy a missing schema or turn a partial migration READY. Older code is accepted only when its declaration explicitly lists the deployed schema version and all of its required field/index definitions remain identical. Package identity/digest verification remains the verified package repository's responsibility; this verifier checks storage compatibility rather than independently authenticating package contents.

`JdbcStateJournal` provides durable lifecycle CAS with independent write revision, first-insert collision handling, query timeout, bounded journal read and outcome-unknown errors after uncertain commit. This does not itself establish multi-node lifecycle ownership. The runtime remains single-instance and trusted-plugin-only, not an OS sandbox.

These tests are prepared but NOT_RUN while dedicated MySQL is unavailable. They never run through the plugin migration API, and restore the tested definition after each successful rejection. ## Optional native deployment endpoints

`FcpStorageDeploymentConfiguration` adds no replacement DataSource bean. Migration is disabled unless `fcp.runtime.storage-deployment.enabled=true` and the server privately configures `FCP_STORAGE_DEPLOYMENT_JDBC_URL`, `FCP_STORAGE_DEPLOYMENT_USER`, and `FCP_STORAGE_DEPLOYMENT_PASSWORD`. Startup checks actual `CURRENT_USER()`, selected database and MySQL server UUID: deployment and runtime must address the same database/server with different account names. No HTTP request accepts credentials or connection settings. Missing configuration produces explicit `DEPLOYMENT_NOT_CONFIGURED`; it never falls back to runtime credentials for DDL. Protect server settings as secrets and grant deployment credentials only to this control-plane process.

All routes require explicit native authorization headers, the platform tenant, fresh `fcp:plugin:install` permissions and live host authorization:

- GET `/fcp/storage/deployment`: configured/disabled status, no secrets.
- POST `/fcp/plugins/{plugin}/storage/plans`: only `version` and `packageDigest`, resolved against the previously verified immutable archive. Arbitrary manifest/SQL input is rejected.
- POST `/fcp/storage/plans/{planId}/apply`: only the returned `digest` and `idempotencyKey`; plans bind the authenticated owner, package and reviewed migration and expire after five minutes.
- GET `/fcp/storage/operations/{operationId}`: persisted owner-scoped operation receipt.

Apply is synchronous and persists RUNNING before starting DDL. MySQL checkpoints and the operation receipt survive a timeout/restart; a client disconnect is not cancellation. An uncertain reply includes the operation ID and requires reconciliation, not silent replay of unknown side effects. Plan caches do not survive restart; regenerate and review a plan against current durable schema state. The existing package upload path may retain the verified archive even when lifecycle registration correctly refuses an undeployed schema; plan by that verified version/digest, deploy, then retry registration.

`native/NativeStorageDeploymentBoundaryTest.java` uses real Spring configuration classes for unit-only disabled/missing/invalid configuration checks; it is not native HTTP acceptance. `native/MysqlGrantBindingTest.java` runs the real `JdbcPluginPolicy` queries against MySQL, covering package_digest binding, old-grant rejection after upgrade, reviewed regrant, explicit task approval, task expiry, revocation and tenant/scope isolation. Compile that test together with the core storage tests and `host/.../PluginPolicy.java` plus `JdbcPluginPolicy.java`. It requires a fresh dedicated test database before any native lifecycle writes the `plugins` journal and refuses to change an existing one. It creates test grant rows, not accounts; no cleanup or production data mutation is performed. Actual native HTTP, separate-account connection verification and MySQL grant/drift tests remain NOT_RUN/BLOCKED in this workspace.
