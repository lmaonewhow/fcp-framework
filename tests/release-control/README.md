# System release controller and executor contract

This module manages **system releases**, not Git branches. `ReleasePlan` binds stable/candidate release IDs and immutable composition digests, environment and the common schema compatibility window. The host must resolve these IDs through its configured `VersionProvider` and independently verify provenance, actual artifacts, current stable deployment, migrations and actual database dirty state in `Preflight`. Declared schema numbers alone are not evidence. The native host remains responsible for authenticated context and platform permission checks.

`ReleaseController(StateJournal, DeploymentProvider, Authorizer, Preflight, Clock)` accepts `TrustedContext`; permissions are `fcp:release:view` and `fcp:release:manage`. `createPlan(context, expectedRevision, operationId, plan)`, `execute(context, expectedRevision, operationId, action, basisPoints)`, `reconcile(context)`, `recover(context, expectedRevision)` and `snapshot(context)` return JSON-compatible maps. The journal is injectable: existing JDBC CAS can be supplied by the production host, and `FileStateJournal` is the single-instance development implementation. The controller does not own/close the journal.

Actions are DEPLOY, CANARY, EXPAND, PAUSE, ABORT, PROMOTE, ROLLBACK and RETIRE. PAUSE freezes the current traffic allocation; ABORT closes **all governed new ingress**, without sending candidate writes to the stable version; ROLLBACK explicitly restores compatible stable routing; RETIRE confirms that the inactive version has drained and been retired. A new plan requires retiring the previous release attempt first. Full promotion updates the stable baseline for the next plan. No action rolls back committed business writes or automatically downgrades schema. Deployment, expansion, promotion, rollback and retirement perform preflight again; incompatible or dirty databases block those actions. PAUSE and ABORT use the saved immutable plan and current authorization/fencing, so a registry outage or dirty database cannot prevent containment.

Before an external effect, the complete command and intended generation are saved by CAS. A successful submit does not complete the action: the coordinator checks observed operation ID, release ID, composition digest, actual generation and basis points. Unknown, unhealthy or incomplete observations keep the command pending. Retirement also requires zero in-flight work. Restart reconciles pending receipts and **does not blindly resubmit**. Conflicting IDs, stale revisions and concurrent writers fail. Operation IDs are bound to actor, tenant, plan and action parameters in the durable journal. Audit history is appended and not pruned; journal capacity exhaustion fails closed rather than erasing history.

## HTTP deployment executor v1

`HttpDeploymentProvider` is a concrete protocol client, **not a built-in production deployment server**, Kubernetes adapter, or an assertion that arbitrary hosts support dual deployment. Deployment operators configure its base URI, HTTP client, capabilities and timeout. HTTPS is mandatory except explicitly enabled loopback development HTTP. Redirects are forbidden. Response bodies have a 64 KiB reception limit and a whole-request deadline; credentials are supplied only through deployment-owned transport configuration, never browser input or release plans.

`PUT {base}/operations/{operationId}?environment={environment}` receives `Command.json()` containing operationId, action, plan, basisPoints and generation. Returns HTTP 200/201/202 with exactly `{"operationId":"...","accepted":true}`. The executor must namespace by environment, persist idempotency receipts, reject a different payload for the same ID, enforce fencing generations and safely serialize commands. Transport stacks may retry idempotent PUT internally, so executor idempotency is mandatory even though the coordinator itself never retries an uncertain submit.

`GET` on the same URL returns 404 for unknown (which does **not** authorize resubmission) or HTTP 200 containing exactly operationId, complete, healthy, candidateRelease, candidateDigest, basisPoints, generation, inFlight detail, routingMode (ACTIVE or STOPPED), and outcome (PENDING, SUCCEEDED or FAILED). PENDING requires complete=false; terminal outcomes require complete=true. Execution outcome is distinct from serving health: a failed PAUSE remains FAILED even if the old route and service health are unchanged. The executor's `complete` claim must mean **observed actual state**, not an accepted desired state. It must validate serving-process health/version/artifacts, routing generation and actual drain; `detail` must be sanitized and contain no secrets. The protocol is an adaptation contract, not a cryptographic proof that a remote server is honest. Trusted executor TLS/auth and operational integrity are required.

Recovery is capability-gated and disabled by the five-argument HTTP constructor. The seven-argument constructor explicitly enables `safeRecovery` and/or `fencedContainment` only for verified executors. `GET operations/{id}/recovery?environment=...&commandDigest=...` returns exactly operationId, commandDigest, disposition (NOT_ACCEPTED, ACCEPTED or UNKNOWN). The SHA-256 command digest uses recursively key-sorted JSON. NOT_ACCEPTED must mean authoritative never-accepted, not missing or expired history; a normal 404 remains UNKNOWN. The controller then resends only the original immutable command with `FCP-Conditional-Claim: not-accepted` and `FCP-Command-Digest`. The executor must **atomically claim if absent, deduplicate identical claims, reject changed commands, and fence stale generations before effects**. A race with an earlier submission therefore cannot duplicate the effect. UNKNOWN remains pending without submission; ACCEPTED reconciles receipts.

A terminal complete observation with unhealthy or wrong-allocation state becomes FAILED rather than permanent pending; its actual generation/allocation are retained and ABORT is available. PAUSE/ABORT can complete containment even while a candidate is unhealthy. FULL supports both. ABORT additionally requires observed routingMode=STOPPED; zero candidate percentage alone is insufficient. ABORT retains the prior active-version identity rather than pretending stable rollback succeeded. From ABORTED, explicit ROLLBACK can reopen ACTIVE routing only after full compatibility preflight. An unknown pending command can be superseded only by ABORT and only when the provider explicitly guarantees fenced containment. The abort uses a generation above the pending command; its predecessor remains in audit/operations as SUPERSEDED_BY_FENCED_ABORT. The executor must prevent all late old-generation work from restoring routes or committing control-plane effects. Without this capability pending remains blocked for operator reconciliation. There is no unsafe “forget pending and replay” escape hatch. Existing FCP globally selected plugin runtime is not converted into simultaneous versions by this module.

## Metrics

`MetricsGate` refuses missing, stale, mismatched-generation, insufficient-sample, non-finite, or unknown-write observations. Technical errors and business rejections count separately, so HTTP 200 with all rejected business operations fails. A verified same-release/same-generation security violation yields ABORT even when the metric window is stale. Excessive errors/latency also yields ABORT; insufficient evidence yields PAUSE. `advance` executes those decisions through the same durable path. Its samples must come from a **trusted observation adapter**, not arbitrary browser-provided metrics. This module does not include a Prometheus collector, scheduler, or claim automatic production rollout is installed.

## Test evidence

Run `bash tests/release-control/run.sh` with JDK 17+ (compile target 17). Tests use a real loopback HTTP protocol executor fixture which actually starts two HTTP listeners and verifies serving v1/v2 responses and rollback routing. They also verify an actual loopback ingress rejects both candidate/stable POST traffic with HTTP 503 after FULL security abort despite unavailable registry/dirty DB, with no added stable writes; compatible explicit rollback reopens traffic. Slow streaming after response headers and an oversized response verify the whole-response deadline and reception bound. They exercise file persistence, restart reconciliation without replay, wrong-digest observations, CAS conflict, idempotency, permission denial, pause, drain, schema rejection, and metric failure modes. This fixture is **not** the native RuoYi host, a real plugin subprocess deployment, MySQL schema migration, or a browser test. Those remain separate integration acceptance requirements.
